# Проєкти та збірки (для адміністратора)

Лаунчер 0.2 більше не прив'язаний до однієї збірки. Гравець при першому запуску вводить
**код проєкту** і свій нік, а далі бачить усі збірки цього проєкту.

## 1. Як код перетворюється на список збірок

```
Код "MY-SERVER"
   └─► projects.json у репозиторії лаунчера (hodiw1/minecraft-fcl, гілка main)
          └─► instances.json у репозиторії проєкту
                 └─► manifest.json кожної збірки (той самий формат, що й раніше)
```

### projects.json — у корені репозиторію лаунчера

```json
{
  "projects": {
    "MY-SERVER": {
      "name": "FNAF RP",
      "repo": "hodiw1/fnaf-packs",
      "branch": "main"
    },
    "OLD-SURVIVAL": {
      "name": "Old Survival",
      "repo": "hodiw1/minecraft-fcl"
    },
    "PARTNER": {
      "name": "Partner Server",
      "index_url": "https://example.com/launcher/instances.json"
    }
  }
}
```

- Код порівнюється без урахування регістру (`my-server` = `MY-SERVER`).
- `branch` за замовчуванням `main`, `index` (шлях до індексу) — `instances.json`.
- Для тестів адміністратор може ввести замість коду `owner/repo` або `owner/repo@branch` —
  гравцям ця підказка не показується.

### instances.json — у репозиторії проєкту

```json
{
  "name": "FNAF RP",
  "description": "Рольовий сервер",
  "instances": [
    {
      "id": "legacy",
      "name": "Legacy",
      "description": "Основний політичний сервер, сезон 2",
      "manifest": "legacy/manifest.json",
      "server": "play.example.com:25565",
      "image": "https://raw.githubusercontent.com/hodiw1/fnaf-packs/main/legacy/cover.jpg",
      "recommended_ram_mb": 6144
    },
    {
      "id": "new-horizon",
      "name": "New Horizon",
      "description": "Технічна збірка з Create",
      "manifest": "new-horizon/manifest.json",
      "server": "nh.example.com:25570"
    }
  ]
}
```

| Поле | Обов'язкове | Що робить |
|---|---|---|
| `id` | так | Назва папки `instances/<id>/`. Лише `a-z`, `0-9`, `-`, `_`. **Не змінюйте** після релізу — інакше гравці качатимуть збірку заново. |
| `name` | ні | Велика назва на головному екрані. |
| `description` | ні | Людський опис замість технічного шляху. |
| `manifest` | ні | Відносний шлях від `instances.json` або повне `https://`. За замовчуванням `<id>/manifest.json`. |
| `server` | ні | `host:port` для індикатора «Сервер онлайн · 12/100». SRV-записи не підтримуються — вказуйте порт явно. |
| `image` | ні | `https://` картинка-фон (≈1280×720, JPG до 300 КБ). |
| `recommended_ram_mb` | ні | Підказка в налаштуваннях ОЗУ. Можна вказати й у `manifest.json`. |
| `size_mb` | ні | Розмір для кнопки «Встановити ~650 МБ». Якщо не вказано — рахується з `manifest.json`. |
| `minecraft_version`, `loader` | ні | Бейджі до завантаження маніфесту. Зазвичай не потрібні. |

### Сумісність зі старим форматом

Якщо `instances.json` немає, лаунчер шукає `manifest.json` поруч і показує одну збірку з id `main`.
Тобто поточний репозиторій `hodiw1/minecraft-fcl` працює як проєкт без жодних змін —
достатньо додати його код у `projects.json`.

`manifest-builder` і далі генерує `manifest.json` однієї збірки. Для кількох збірок у одному
репозиторії запускайте його в окремих папках/гілках або тримайте кожну збірку в окремому репозиторії
й посилайтесь на `manifest.json` повним `https://`.

## 2. Розкладка файлів у гравця

```
%AppData%\com.custom.mclauncher\     config.json, skins\, projects\ (кеш)
<папка лаунчера>\                     змінюється в Налаштуваннях
  minecraft\   versions, libraries, assets — СПІЛЬНІ, без дублювання
  runtime\     Java — спільна
  instances\
    legacy\        mods, config, resourcepacks, shaderpacks, servers.dat, saves, options.txt…
    new-horizon\
```

## 3. Що лаунчер робить із файлами збірки

- **Грати** — швидка перевірка (розмір + записаний SHA-256), докачування змінених файлів,
  видалення зайвих `.jar` у `mods/`.
- **Ремонт** — повний SHA-256 кожного файлу + перевірка бібліотек і ресурсів Minecraft.
- `config/*` і `servers.dat` докачуються, лише якщо їх немає або **адмін змінив** їх у маніфесті.
  Правки гравця не перезаписуються.
- Ніколи не чіпаються: `options.txt`, `optionsof.txt`, `optionsshaders.txt`, `saves/`, `screenshots/`,
  `xaero*/`, `journeymap/`, `logs/`, `crash-reports/`.
- Пресет графіки й мова гри пишуться в `options.txt` **один раз** — коли файлу ще немає
  (перше встановлення), або вручну кнопкою в Налаштуваннях (лише графічні ключі).

## 4. Скіни

Скін профілю копіюється в `instances/<id>/CustomSkinLoader/LocalSkin/skins/<нік>.png`.
Щоб гравець бачив свій скін, додайте в збірку мод **CustomSkinLoader**.
Щоб скін бачили інші — потрібен плагін на сервері (наприклад, SkinsRestorer).

## 5. Картинки проєкту та збірок

Лаунчер сам підтягує картинки з репозиторію проєкту. Нічого прописувати в JSON не потрібно —
достатньо покласти файли з **точно такими іменами** (малими літерами):

```
<репозиторій проєкту>/
  icon.png                         іконка проєкту (сайдбар, верхня панель, вкладка «Проєкт», список проєктів)
  projects.json                    необов’язково: назва проєкту з правильним регістром
  instances/
    <id збірки>/
      manifest.json
      icon.png                     іконка збірки (картки в списку збірок)
      1.png, 2.png, 3.png, …       слайд-шоу на головному екрані збірки (пріоритет №1)
      bg.png                       один фон головного екрана збірки (пріоритет №2)
```

- **icon.png** — квадрат, 256×256 (мінімум 128×128), PNG.
- **Фон збірки: спершу нумерована серія, потім одиночний фон.**
  1. **`1.png`, `2.png`, `3.png`, … — слайд-шоу.** Якщо в папці збірки є `1.png`, лаунчер бере всю серію
     `1.png..N.png` (без обмеження кількості) і **ігнорує** `bg.png` та інші запасні фони.
     - Імена — лише `<число>.png` малими літерами, без нулів на початку (`1.png`, а не `01.png`; `0.png` не рахується).
       Кадри йдуть за числом: `1, 2, …, 9, 10, 11`.
     - Якщо список файлів збірки видно через GitHub API (у проєкті немає `instances.json` —
       збірки знаходяться автоматично), беруться всі такі файли, навіть із пропусками в нумерації.
       Інакше (є `instances.json`, або GitHub API недоступний) лаунчер перевіряє `1.png`, `2.png`, `3.png`, … по черзі
       через raw/дзеркала до першого відсутнього файлу, тож **нумеруй без пропусків**. Якщо немає `1.png`, далі не перевіряється.
     - Якщо кадрів 2 або більше, вони змінюються по колу кожні ~7 секунд із плавним кросфейдом (~1 с).
       Наступний кадр завантажується заздалегідь. Слайд-шоу стоїть на паузі, коли вікно згорнуте або запущена гра,
       а якщо в системі ввімкнено «зменшення руху» (prefers-reduced-motion), показується лише `1.png`.
       Якщо кадр лише один (`1.png`), він показується статично.
     - У картці збірки в списку завжди показується `1.png`.
  2. **`bg.png` — один фон**, якщо `1.png` немає. Шукається в такому порядку: `bg.png`, `bg.jpg`,
     `background.png`, `background.jpg`, `background.webp`, `banner.png`, `banner.jpg`. Береться перший, що існує.
     Якщо в `instances.json` у збірки вказано `image` (повне `https://`), воно має пріоритет над `bg.png`,
     але не над серією `1.png..N.png`.
- Розмір кожного кадру — 1920×1080 (16:9), до ~500 КБ. Головне — ліва й нижня частини картинки:
  там лежать назва й кнопки, лаунчер їх затемнює.
- Якщо фону немає (404), показується перша літера назви та стримана текстура замість фону.
- Лаунчер пам’ятає знайдені картинки й серії 6 годин, а відсутні — 30 хвилин, тож нові кадри
  чи картинки з’являться у гравців не миттєво (кнопка «Синхронізувати» оновлює список, переданий через GitHub API, одразу).

### Назва проєкту з правильним регістром

Назва репозиторію на GitHub зазвичай у нижньому регістрі (`terrapolis-myteam`). Щоб гравці бачили «MyTeam»,
вкажи назву в `projects.json` у корені репозиторію проєкту:

```json
{ "name": "MyTeam" }
```

Підходить і формат `{"projects": {"MyTeam": {...}}}` — береться ключ, що збігається з назвою репозиторію.
Також назву можна задати полем `name` в `instances.json`. URL репозиторію завжди формується в нижньому регістрі.

## Дзеркала (Multi-Mirror Fallback) та офлайн-режим

Кожен запит до файлів із GitHub-репозиторію (`projects.json`, `instances.json`, `manifest.json`,
моди збірки) лаунчер виконує з автоматичним перебором дзеркал. Якщо джерело повертає мережеву помилку,
таймаут, HTTP `403`, `404`, `429`, `451`, `5xx` або сторінку-заглушку замість JSON, лаунчер пробує
наступне дзеркало. Посилання `raw.githubusercontent.com/...` із `manifest.json` при цьому підмінюються
на дзеркала, а SHA-256 файлу все одно перевіряється. Хост, що не відповідав, на 5 хвилин переноситься
в кінець черги.

Список дзеркал збирається так (дублікати прибираються):

1. `<AppData лаунчера>/mirrors.custom.json` — власні дзеркала гравця/адміна, лаунчер його не перезаписує;
2. віддалений конфіг `MIRRORS_CONFIG_URL` (за замовчуванням `mirrors.json` у корені репозиторію лаунчера),
   останню успішну копію лаунчер кешує в `<AppData лаунчера>/mirrors.json`;
3. вбудовані `CONTENT_MIRRORS` / `UPDATE_MIRRORS` з `src-tauri/src/constants.rs`.

Формат (однаковий для всіх трьох джерел):

```json
{
  "content": [
    "https://raw.githubusercontent.com/{owner}/{repo}/{branch}",
    "https://cdn.jsdelivr.net/gh/{owner}/{repo}@{branch}",
    "https://my-mirror.example.com/{owner}/{repo}/{branch}",
    "https://proxy.example.com/{url}"
  ],
  "update": [
    "https://api.github.com/repos/{owner}/{repo}/releases/latest",
    "https://my-mirror.example.com/terrapolis/update.json"
  ]
}
```

- `{owner}`, `{repo}`, `{branch}` беруться з оригінального посилання, шлях до файлу дописується в кінець.
- `{url}` — повне оригінальне посилання (для проксі; працює і для файлів із GitHub Releases).
- Шаблони мають починатися з `https://`.

Якщо недоступні всі дзеркала, лаунчер показує збережений список (або лише встановлені збірки) і запускає
встановлені збірки з локальної копії маніфесту — статус «Офлайн-режим» видно у верхньому рядку та на
головному екрані.

### Імпорт збірки з .zip

Кнопка **Імпорт** на головному екрані (або «⋯ → Імпортувати з .zip…») встановлює збірку з архіву без
інтернету. З архіву беруться лише `manifest.json`, `mods/`, `config/`, `resourcepacks/`, `shaderpacks/`
та `servers.dat` (корінь збірки шукається автоматично за `manifest.json`). Світи, скріншоти й
`options.txt` гравця не змінюються. Кнопка з архівом у групі «Власні збірки» створює з архіву нову
власну збірку.

### Дебагер збірки

Перед кожним запуском збірки проєкту дебагер звіряє `mods/` з `manifest.json`: докачує відсутні моди,
замінює пошкоджені (SHA-256) і переносить сторонні `.jar` у `instances/<id>/.launcher/removed-mods/`
(звідти їх можна повернути). Власні збірки гравця дебагер не чіпає. Ручний запуск з повним звітом —
«⋯ → Перевірити збірку (Дебагер)».

## Оновлення лаунчера

Інформацію про нову версію лаунчер бере з `UPDATE_MIRRORS`: спершу GitHub Releases API (`tag_name`,
`body`, `published_at`, `.exe` в `assets`), а якщо API недоступне чи вичерпано ліміт, з `update.json`
у корені репозиторію (або на будь-якому дзеркалі):

```json
{
  "version": "0.3.0",
  "date": "2026-12-01T12:00:00Z",
  "notes": "## Що нового\n- ...",
  "url": "https://github.com/hodiw1/terrapolis/releases/download/v0.3.0/launcher.exe",
  "sha256": "<sha256 launcher.exe>",
  "size": 12345678
}
```

У Налаштуваннях → «Оновлення лаунчера» гравець вмикає автооновлення (`auto_update_launcher`, за
замовчуванням вимкнено). Без нього лаунчер показує сповіщення `vX → vY` з кнопками «Пізніше»,
«Що нового» (повний опис релізу) і «Завантажити».

## CurseForge API-ключ

Пошук модів на Modrinth працює без ключа. Для CurseForge потрібен ключ CurseForge Core API
(console.curseforge.com → API keys). Гравець вставляє його в Налаштуваннях → «Джерела модів»
(зберігається в `config.json` як `curseforge_api_key`); альтернатива — змінна середовища
`CURSEFORGE_API_KEY` (або `TERRAPOLIS_CURSEFORGE_KEY`).
